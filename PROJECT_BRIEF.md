# Competitor — PROJECT_BRIEF.md (single source of truth, read at the start of every task)

## Product
Maths tutor for Putnam/ICMC students that never gives the solution first. It compares HOW the expert reads a problem versus HOW the student reads it, cue by cue, through one shared schema anchored to phrases of the problem text. Protocol name: ProofReader. Not a chatbot: the dashboard is a workflow document, never a message box. Never a verdict on who did better.

## Data
`USE_MOCK=true` in .env.local -> `/api/analyse` returns the matching hand-written analysis from `lib/dummy/` by problem id (ICMC 2019 P1–P2 and 2020 P6; also the model's quality target); unknown problems get an honest 501. `false` -> real calls via openai SDK to https://api.meta.ai/v1, model muse-spark-1.3, key MODEL_API_KEY (JSON mode + zod validation with one errors-appended retry in `lib/providers/meta/client.ts`); call A (effort high) at `/api/analyse`, calls through images at `/api/read` (purpose "attempt" = call C, or "statement" = photo transcription) via `lib/providers/meta/vision.ts`; `/api/solve` runs call S and `/api/explain` the feedback pass; the comparison stays the empty state until compare.ts lands. Browser never calls Meta directly: uploads (photos, HEIC, multi-page GoodNotes PDFs) become ≤8 downscaled JPEG data URLs client-side in `lib/pages.ts` (lazy pdf.js + heic2any; the student removes/reorders pages, picking this problem's pages out of a multi-problem PDF by hand). Successful analyses are cached per problem in localStorage (`lib/analysisCache.ts`), so revisits and resubmits skip call A for an unchanged statement. `npx tsx scripts/expert-pass.ts <dummy-id|file>` runs call A from the terminal; `npx tsx scripts/attempt-pass.ts <fixture-id>` runs call C over git-ignored fixtures/ and reports structure, span matching, retry, duration, tokens.

## Pipeline (all live: S, A, B, C, explain)
Call S: private solve (high) + sceptical verify (medium) in `lib/providers/meta/solve.ts` — route, key steps, final line, and a small case executed in full arithmetic that the verifier recomputes from scratch; one corrected re-solve on a fail; `solution.verified` records the verdict. The solution is grounding only: carried on AnalysisSchema, cached, NEVER rendered (the product never shows a solution). Call A: expert pass (high), grounded when a verified solution exists — the kept method must be the solution's route, weights follow what it uses, simplification is its small case, nothing echoes the answer; an unverified draft is dropped silently. Call B: second reading (medium, `reweighPrompt.ts`) — the complete updated chain: weights move, ≤2 spans join, second_reading records the pass; failure keeps the first reading. Call C: student extraction from attempt pages (medium, `attemptPrompt.ts`): faithful not charitable, evidence-less stages stay empty, spans quote the statement verbatim, attempt_report records structure/inferred/missing/legibility; unguided attempts get the calm AttemptNotice. Explain call (medium, `explainPrompt.ts`): writes the comparison as elaborated feedback from the solution + both chains + the authoritative TS skeleton, under binding research rules — process level never person level (Hattie & Timperley 2007; Kluger & DeNisi 1996), elaboration over verification with ≤3 ranked cards (Shute 2008), evidence quoted and located (Sadler 1989), redirection stopping short of the solution (VanLehn 2011), near-miss framed as a control decision to revisit (Schoenfeld 1985; Mueller & Dweck 1998), a self-check per card (Nicol & Macfarlane-Dick 2006). `lib/compare.ts` computes the authoritative skeleton and is the fallback when the explain call fails. Render progressively; never one long spinner. Stretch: ablation, one deciding cue removed at a time.
Honest framing the UI keeps: a grounded reading says "grounded in a route the expert solved and verified on a small case; the solution stays private"; an ungrounded one keeps "a plausible narrative, not the model's cognition". Ablation is the measured counterpart.

## Schema (shared by expert and student chains)
problem{text} — the statement exactly as typed: prose with $…$/$$…$$ maths, the single source string (write \% for a literal percent; avoid stray unpaired $). spans[{id,text,category,weight 0-100,reason}], reading{cues[{id,span_id,why_it_matters,how_spotted}],definitions[{term,meaning_latex}]}, goal{asked,answer_form,final_line_would_say}, informal_cues[{span_id,bearing}], abstraction{underneath[{object,really_is,implies}],deeper_properties[]}, simplification{instance,instance_latex,what_to_try,notice_prompt}, method{candidates[{name,deciding_span_ids,from_first_principles,kept,why}],chosen}, prerequisites[{name,needed_for,flag assumed|needed}], second_reading{new_spans,reweighted[{span_id,old,new,why}],what_changed}, domain "maths"|"not_maths".
Rules: every span is an exact substring of problem.text, checked in code — spans quote the source verbatim, so inside a formula a span is raw LaTeX (e.g. 3^0\binom{2020}{0} - …); the dashboard renders the statement as KaTeX with highlights sliced at span boundaries (a span that cuts a formula where the piece is not renderable standalone highlights the whole formula); every prose field renders $…$ inline maths; zod validates every model response; comparison is TypeScript set difference (currently hard-coded in dummy data — `lib/compare.ts` pending). The comparison is where_you_are / first_divergence / ≤3 ranked FeedbackCards (kind near_miss|wrong_turn|missed_cue|unused_mark; evidence_student quoted and page-located, expert_span_ids, diagnosis, redirection short of the solution, self_check) / unused_cues / where_to_next; student spans may be flagged `uncertain`; AnalysisSchema optionally carries attempt_report and the private solution. `/api/analyse` serves through the `lib/analysis.ts` provider seam (mock, or real `lib/providers/meta.ts` with call A wired; `AnalysisInput` lives in `lib/providers/types.ts`).

## Stack and rules
Next.js 15 App Router, TypeScript strict, Tailwind, zod, openai, katex. API routes only, no DB, no auth. Files are split by responsibility: each component does one thing, and a file is too long when it does two things, not when it passes a line count. Boring readable code; validate at the boundary; explicit loading/error states; no fetch-on-mount for user work. After every change: build, lint, verify, report.
